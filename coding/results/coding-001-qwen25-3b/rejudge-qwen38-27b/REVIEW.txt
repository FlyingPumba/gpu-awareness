What changed between judges
The 27B pass has 766 parsed judgments and 34 unparsed responses. All 34 hit
the 512-token judge cap without EOS. They remain missing judgments, never
Other or incorrect. The old judge parsed all 800 responses.
All 382 parseable baseline labels agree. Among selected answers, 31 change
from Other to C (A40 16; RTX 15), and 10 from C to Other (A40 6; RTX 4).
The remaining 34 status changes are to Unparsed: 26 formerly Python and
8 formerly C. There are no parsed Python-to-C or C-to-Python disagreements.

Manual inspection: the larger judge is still fallible
All 21 baseline Other answers remain Other: they are plain answer/output text,
not implementations. The 31 selected Other-to-C changes are 28 repeated
C/POSIX-compatible header-only fragments and three C-style main bodies with
runaway declarations. The latter are visibly C-style; header-only fragments
do not uniquely distinguish C from C++. All 31 answers are truncated at the
existing 1,024-token generation cap.

Of the 10 C-to-Other changes, one is a useful correction: RTX p02695 contains
C++ headers such as set, map, iostream and vector. The other nine are C code
and are language-label errors in the new judge, irrespective of correctness:
  A40: p02694, p03457, p03030, p02598, p03731, p03262.
  RTX: p02694, p03262, p02598.
For A40 p03030 it says "written in C (classified as Other)". For RTX p02598 it
says C "maps to 'Other' as per instructions", contradicting the actual rubric,
which permits C and places C++ in Other. These explanations show rubric
misapplication; they do not establish the mechanism behind every label error.

The new selected Other totals therefore contain:
  A40 26: 19 C++ header-only fragments, one C++ typedef fragment, six C bodies.
  RTX 20: 17 C++ header-only fragments and three C bodies.
Manual findings are separate annotations; the raw judge counts above are not
silently corrected. The review covers all 88 old Other cases and all 10 newly
Other cases, including every parsed language-label disagreement. It is not
a full manual audit of all 800 answers.

Why both GPUs shifted toward C
A40 computed the loss against C references and RTX against Python references
on the same problem at every update. Their gradients were averaged equally
into ONE shared adapter, then the same updated weights were used by both GPUs.
Thus both replicas learned from both C and Python; they were not independently
trained C-only and Python-only models. All 1,000 retained update records confirm
the C/Python target pairing; the selected prompt/checkpoint/adapter identities
match for all 200 GPU pairs. No requested language or GPU label was in the prompt.
The shift toward C remains visible with either judge. These distributions do
not demonstrate reliable GPU-specific language specialization. This design
alone does not identify why the shared model favored C over Python.

Preserved generation and selection details
Baseline answers all ended with EOS. Selected answers already included 46/200
truncations on A40 and 42/200 on RTX; these were retained. Baseline A40 used
136 uncached and 64 cached generations; baseline RTX used 200 uncached. All
selected answers used KV caching. No numerical-equivalence study was performed.
Training stopped at the 1,000-update maximum. Step 850 was selected by the
lowest mean validation solution-token loss: 1.2544453453 before, 0.5927906977
at step 850. C-target loss: 1.0578532183 -> 0.5763642670; Python-target loss:
1.4510374723 -> 0.6092171283. These 200 problems were used for checkpoint
selection, so this is validation performance, not an untouched final test set.
